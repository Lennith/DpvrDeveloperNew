Content Distribution and Download¶

The server notifies devices about resources through RDC content-list messages. RDC transports the list and reports status; it does not host the resource files. Resource files must be deployed on an HTTP/HTTPS service reachable by the device.

Sending a Content List from the Server¶

The server library provides the following two methods:

public void SendContentList(string sn, List<Message.ContentItem> contents)
public void SendContentListToClients(List<Message.ContentItem> contents, List<Client> clientList = null)

SendContentList sends to one connected client selected by SN. SendContentListToClients sends to all clients when clientList is null.

Content item structure:

public class Message.ContentItem
{
    public string content_id;
    public string file_name;
    public string url;
    public long size;
    public string hash;
    public string version;
}

content_id is the unique identifier used to create the task and associate status reports. The client ignores an item without this field. file_name is also required, may contain UTF-8 characters including Chinese, and must be a single file name without /, \, %, ?, #, or path fragments such as ...

url is required, must use HTTP or HTTPS, and is passed unchanged to the device-side download service. Deploy resources at an address reachable by the device, for example:

http://192.168.1.100/dpvr/content/demo.mp4

Nginx or the IIS/HTTP service included with Windows can serve this directory. Before testing, confirm that the device can access the URL and that the HTTP service allows access from the device network; the RDC server does not proxy or host the file.

Device-side Download Flow¶

After receiving a 4001 content list, the current client implementation:

  1. Calls ContentDownloadManager.addContentTask for each item with valid content_id, file_name, and url fields.

  2. Binds the external com.dpvr.downloadmanager/.DownloadService component.

  3. Creates a task with IDownloadManager.addTaskSimple(url, PRIORITY_SYSTEM, "contents/<file_name>", true) and starts it automatically.

  4. DownloadService uses Android DownloadManager to write the file into the contents subdirectory of the system public Downloads directory, typically /storage/emulated/0/Download/contents/<file_name>.

The download service uses Android DownloadManager.Request(Uri.parse(downloadUri)) and setDestinationInExternalPublicDir(Environment.DIRECTORY_DOWNLOADS, downloadFilePath). The application explicitly allows cleartext HTTP downloads, so resources can use an HTTP or HTTPS URL reachable by the device. The RDC client does not add or implement a DownloadService entry; it uses the existing IDownloadManager AIDL wrapper and does not require a new IDownloadService.aidl in the RDC project.

Compatibility requirement: the DPDownloadService included in the device firmware must support the public Download/contents destination and HTTP/HTTPS downloads described above. The older alpha implementation uses an empty directory type and writes files under the external-storage root instead of the public Download directory, so it is incompatible with the current RDC path contract. Update that system service before testing content deployment.

The download AIDL methods currently used by the RDC client include:

int addTaskSimple(String uri, int priority, String downloadFilePath, boolean autoStart);
int startTaskById(int taskId);
void stopTaskById(int taskId);
void removeTaskDownloadFileById(int taskId);
void registDownloadStateListener(IDownloadStateListener listener);
void unregistDownloadStateListener();

The cross-process DownloadTask Parcelable order is taskid, downloadUri, priority, downloadFilePath, autoStart. A shared service package name does not mean that different historical AIDL or Parcelable definitions can be mixed.

One-shot execution semantics¶

A 4001 content list is a one-shot execution command, not a durable pending queue: the server sends it once, the device executes it once, and reports the current state with 4002. A TCP/Wi-Fi disconnect, device reconnect, or heartbeat timeout does not cause RDC to resend 4001 automatically; the device also does not create or retry a task merely because the connection is restored. To execute a download again, the server must explicitly send the corresponding 4001 content item again. Sending the same content_id again means re-execute: the RDC caller removes the old task and file through Binder before creating the new task. Automatic retry and resumable-download behavior are not guaranteed.

Status Reporting¶

The client reports content status with message 4002 every two heartbeats; the heartbeat interval is 2 seconds. contents is a complete snapshot of the device-side records, not a delta; an empty array is sent when no records remain, and the server should replace its stored records with the snapshot.

{
  "sn": "device serial number",
  "contents": [
    {
      "content_id": "demo-video",
      "status": "downloading",
      "progress": 42,
      "downloaded": 0,
      "local_path": "file:///storage/emulated/0/Download/contents/demo.mp4",
      "error": null
    }
  ]
}

status is currently mapped to pending, downloading, waiting, finished, idle or error; progress is a percentage; and local_path comes from DownloadService. Progress callbacks do not overwrite the current status; when DownloadService reports an error without a more specific detail, the caller uses download_failed. The current ContentManager does not calculate downloaded or validate the hash. Validation or task-creation failures may set error to invalid_file_name, invalid_url or download_task_create_failed. DownloadService does not own application-level timeout, retry, or resume policy; the Binder caller handles subsequent processing. Tests should primarily use status, progress, and local_path as acceptance signals.

finished means that DownloadService/Android DownloadManager reported the task as successful; it does not imply hash validation. When building the 4002 snapshot, the RDC client checks local_path and removes a finished entry whose file was externally deleted. The server then clears the corresponding stored record when it receives the replacement snapshot; the client does not automatically redownload the file. To redeploy or restore it, the server must explicitly send the corresponding 4001 content item again.
