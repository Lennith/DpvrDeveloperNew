Server Development Based on Communication Protocol¶

The client maintains a long connection with the server through TCP, and all communication between the two ends uses the same message encapsulation.

Communication Data Format¶

[2Bytes data length] [2Bytes data type] [2Bytes reserved] [Data body]

data length : 2Byte Short, representing the length of the message content, including the message header.

data type : 2Byte Short, representing the type of the message, used to distinguish the type of message.

resevered : 2Byte Short, reserved for future use, currently set to 1.

data body : JSON-formatted message content, using UTF8-String, which is the message type structure described below.

For example, the Java encapsulation of the message packaging method is as follows:

public static byte[] createMessageByJson(String jsonBody,short msgType){
    short size = (short) (jsonBody.length() + 6);
    if(size <= 6) return null;

    ByteBuffer bf = ByteBuffer.allocate(size);
    bf.putShort(size);
    bf.putShort(msgType);
    bf.putShort((short)1);
    bf.put(jsonBody.getBytes());
    bf.flip();
    byte[] result = new byte[size];
    bf.get(result);
    Log.d(TAG,"msg size: "+ size + "type" + msgType + " json: " + jsonBody );
    return result;
}

Body Types¶

The body of client communication messages varies according to the type and has different data structures. They are serialized into JSON structures.

Client Heartbeat¶

Heartbeat information sent by the client to the server, including some client information.

Type : 1001

Body :

class Client_Heart_Beat {
    String hardware;
    int battery_level;
    String top_apk;
    String cast_rtsp_url;  // Empty when Cast is not active
    Player_Status player_info; // Optional, see description below
}

hardware : Device SN number.

battery_level : Battery level, 0~100.

top_apk : The package name of the application currently displayed at the top.

cast_rtsp_url : The current DPVR Cast RTSP address. It is an empty string when Cast is inactive, DMS is disconnected, or the device IPv4 address is unavailable. After the client receives the DMS Cast state event, the format is rtsp://<device IPv4>:8554/stream1.

player_info : Optional field, playback progress information. Included only when top_apk contains com.dpvr.videoplayer (i.e., the DPVR video player is in the foreground) and the client has received player status.

class Player_Status {
    float time;     // Current playback position
    float duration; // Total video duration
    String state;   // Player state
    String name;    // Video name
    String path;    // Video path
}

Note

The values of player_info are passed through from the DPVR player broadcast (com.dpvr.videoplayer.playerstatus). The client caches the latest status and attaches it to each heartbeat; the heartbeat interval is 2 seconds, and the freshness of the progress data depends on the player’s status broadcast frequency. Older server libraries ignore this field (remaining compatible); use the new LibDpvrRDC to parse playback progress.

Content List¶

The server sends a content list to the client. After receiving it, the client automatically creates and starts a download task for each item with valid content_id, file_name, and url fields.

Type : 4001

Body :

class Content_List {
    String sn;                 // Optional; useful for targeted delivery
    List<Content_Item> contents;
}

class Content_Item {
    String content_id;
    String file_name;
    String url;
    long size;
    String hash;
    String version;
}

content_id : Unique content identifier. The client ignores an item that does not contain this field.

file_name : Required destination file name. UTF-8 names, including Chinese, are allowed. It must be a single file name and must not contain /, \, %, ?, #, or path fragments such as ...

size, hash, version : Content metadata. The current RDC client does not perform additional size/hash/version validation.

url : Required resource address. It must use HTTP or HTTPS and is passed unchanged to the device-side DownloadService, for example http://192.168.1.100/dpvr/demo.mp4. Resources can be hosted by Nginx or the IIS/HTTP service included with Windows; the RDC server itself does not provide file hosting.

The client uses contents/<file_name> as the relative destination. DownloadService writes the resource into the contents subdirectory of the system public Downloads directory (typically /storage/emulated/0/Download/contents/<file_name>) and starts each task with autoStart=true. The device-side service component is com.dpvr.downloadmanager/.DownloadService.

Content Status Report¶

The client reports content download progress with the following message.

Type : 4002

Body :

class Content_Report {
    String sn;
    List<Content_Report_Item> contents;
}

class Content_Report_Item {
    String content_id;
    String status;
    int progress;
    long downloaded;
    String local_path;
    String error;
}

status is currently mapped by the client to pending, downloading, waiting, finished, idle or error. progress is a percentage, and local_path is the local path returned by DownloadService. The client does not calculate downloaded; its value remains 0. Validation or task-creation failures may set error to invalid_file_name, invalid_url or download_task_create_failed. The client sends a report every two heartbeats (the heartbeat interval is 2 seconds), including contents=[] when no content entries remain.

4001 is a one-shot execution command. Sending the same content_id again means re-execute: the client removes the old task and file through the DownloadService Binder before creating the new task. The client does not retry merely because the connection is restored, and resumable-download behavior is not guaranteed. The contents array in 4002 is a complete snapshot of the device-side records, not a delta; an empty array clears the corresponding stored content records on the server.

Client Passthrough¶

Passthrough message sent by the client application to the server.

Type : 3001

Body :

class Client_Message {
    String from_package;
    String body;
}

from_package : Package name of the application sending the message.

body : Message content.

Play Video¶

Message sent by the server to the client to play a video.

Type : 1002

Body :

class Play_Video {
    String VideoType;
    String VideoPath;
    int StereoType;
    boolean StartOnPrepared = false;
}

VideoType : Video type, fixed as “*”.

VideoPath : Video path.

StereoType : Video display format.

Note

0 : Standard 2D video.

1 ： 3D left-right.

2 ： 3D top-bottom.

3： 180-degree 2D.

4 ：180-degree left-right 3D.

5： 180-degree top-bottom 3D.

6： Panoramic 2D.

7： Panoramic left-right 3D.

8： Panoramic top-bottom 3D.

StartOnPrepared : Whether to start playback automatically once the video is prepared.

Pause Video¶

Message sent by the server to the client to pause the current video playback.

Type: 1003

Body: null

Stop Video Playback¶

Message sent by the server to the client to stop the current video playback. This command only stops playback and does not affect the RDC connection; whether the player UI is also closed is determined by the player application itself.

Note

The client selects the stop route used by the most recent 1002 command: it sends com.dpvr.videoplayer.VIDEOPLAYERCONTROLLER when the DPVR player is used, or com.deepoon.dpnlauncher.PLAY_CONTROL with controltype=playcommand and operation=stop when playback falls back to DpnLauncher. The command does not affect the RDC connection; whether the player UI exits is decided by the player application.

Type : 1004

Body : null

Resume Video Playback¶

Message sent by the server to the client to resume the current video playback at a specified unified moment.

Type : 1005

Body :

class Push_Resume_Video {
    String PlayTime;
}

PlayTime : The unified resume moment, as a yyyy-MM-dd-HH-mm-ss format string (server local time, second precision, no milliseconds). The server-side VideoResume(delay) API adds delay (in seconds) to the server’s current time to generate this value. For example, if the server time is 12:00:00 and delay=10, PlayTime will be 2026-07-17-12-00-10, and all devices resume playback when their local time reaches 12:00:10.

Note

To use the scheduled resume playback feature, ensure the client system time is synchronized with the server. The client will start playing the video immediately if the current time is greater than the set time.

Seek Video¶

Message sent by the server to the client to execute the Seek command during video playback.

Type : 1006

Body :

class Push_Seek {
    int time;
}

time : Video seek position, in seconds.

Set System Volume¶

Message sent by the server to the client to set the system volume.

Type : 1007

Body :

class Push_Set_Vol {
    int volume_value;
}

volume_value : Volume value, ranging from 0 to 15.

Block Keys¶

Message sent by the server to the client to block specific keys.

Type : 1008

Body :

class Push_Block_Key {
    int block_power_key;
    int block_back_key;
    int block_home_key;
    int block_touch;
    int block_volume_key;
}

block_power_key : Block power key, 1: block, 0: do not block.

block_back_key : Block back key, 1: block, 0: do not block.

block_home_key : Block home key, 1: block, 0: do not block. On devices without a physical home key, this will block the home key on the controller.

block_touch : Block touchpad, 1: block, 0: do not block.

block_volume_key : Block volume keys, 1: block, 0: do not block.

Type : 1009

Message sent by the server to the client to restart.

Type : 1010

Body : null

Message sent by the server to the client to recalibrate the headset view, effective only for VR applications using the DpvrSDK.

Type : 1011

Body : null

Start DPVR Cast¶

Message sent by the server to the client to call the device-side DMS interface and start the screen RTSP stream.

Type : 1012

Body : Empty JSON object {}.

The client calls mediaJobs/StartMiracast through the existing DeviceManager client wrapper. RDC does not implement a duplicate DMS service entry. The start result is reported asynchronously through the DMS dpvr_cast_state event; cast_rtsp_url is updated in a subsequent heartbeat.

Stop DPVR Cast¶

Message sent by the server to the client to call the device-side DMS interface and stop the screen RTSP stream.

Type : 1013

Body : Empty JSON object {}.

The client calls mediaJobs/StopMiracast through the same wrapper. After receiving isCasting=false, subsequent heartbeats report an empty cast_rtsp_url.

Note

When the RDC client connects to DMS, it calls mediaJobs/CheckDpvrMiraCastState to initialize the Cast state and listens for the dpvr_cast_state event’s isCasting field. The device must have the required DMS permission/authorization; successful protocol delivery does not mean that the RTSP stream is already available.

Open Specified Application¶

Message sent by the server to the client to open a specified application.

Type : 2001

Body :

class Start_Activity {
    String packagename;
    String classname;
}

packagename : Application package name.

classname : Activity class name to open.

Note

When the RDC client starts the requested component from its service context, it supplies Android NEW_TASK and MAIN/LAUNCHER launch semantics so Android 12 and the DPVR normal 2D-to-VD route can process the request. On DPVR devices, com.dpvr.VirtualDesktop may host a normal 2D application and place the target Activity on a VD display (for example display2/display4 or the device-assigned virtual display); keeping DpnLauncher as the display0/SVR foreground owner is by design and is not a 2001 failure. The target application and Activity must still be installed, exported, and startable for the current user.

Close Application¶

Message sent by the server to the client to close a specified application.

Type : 2002

Body :

class Stop_Activity {
    String packagename;
}

packagename : Application package name.

The client handles 2002 by stopping the package. It does not require the display0 DpnLauncher or the VD host to exit, and it does not promise a particular foreground UI after the stop.

Server Passthrough¶

Passthrough message sent by the server to the client.

Type : 3002

Body :

class Server_Message {
    String to_package;
    String body;
}

to_package : Package name of the client receiving the message.

body : Passthrough message content.

Note

To use this interface, the application receiving the passthrough message needs to bind (AIDL) to the RDC service and listen for passthrough messages, or complete this through the DpvrDeviceManagerService interface.

Server Example¶

We provide a simple server.net Demo.

This demo demonstrates message encapsulation, protocol packet, and provides a socket server framework based on IOCP for developers to quickly perform secondary development.

The demo uses a console program, where commands can be entered through the console to control the client. Please refer to the Program.cs method in the HandleCmd file for details.

Frequently Asked Questions¶

Q: How can I ensure that all clients start playing the video simultaneously?

A: We recommend the following methods:

  1. Reduce server delay for latency optimization between devices. Ensure the server can control the communication delay of all devices within a relatively stable range. The delay between the slowest and fastest devices should not exceed 100ms. This allows the communication commands to be sent to all devices more smoothly. Our demo example, using about 35 devices in a network environment provided by ASUS AX82U, can ensure the maximum reception delay within 50ms.

  2. If server or network conditions cannot guarantee low latency for all devices, send the start video playback command without enabling StartOnPrepared. Then, set the resume playback time when sending the resume playback command to ensure all devices resume playback simultaneously.

    Generally, the player startup takes about 5 seconds, and loading takes an additional 2-3 seconds. As a reference, we recommend setting the resume playback time to 10-15 seconds after the start playback command is issued.

Note

Ensure the client system time is synchronized with the server when using the timed resume playback feature.

  1. Seek Synchronization: Similarly, if you need to keep devices synchronized after seeking, use the same approach as for synchronized resume playback. Send the seek command and then a timed resume playback command to ensure all devices resume playback at the same point.
