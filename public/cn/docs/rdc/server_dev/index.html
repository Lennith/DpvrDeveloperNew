基于通信协议的服务端开发¶

客户端通过TCP与服务端保持长连接，所有双端间的通信使用相同的消息封装。

通信数据格式¶

[2Byte Size] [2Byte Type] [2Byte Reserved] [Body]

Size : 2Byte Short，表示消息内容的长度，包括消息头。

Type : 2Byte Short，表示消息的类型，用于区分消息的类型。

Resevered : 2Byte Short，保留位，目前为1。

Body : Json格式的消息内容，使用UTF8-String，为下文的消息类型结构。

以客户端心跳为例，它的Java封装如下：

public static byte[] createMessageByJson(String jsonBody,short msgType){
    short size = (short) (jsonBody.length() + 6);
    if(size <= 6) return null;

    ByteBuffer bf = ByteBuffer.allocate(size);
    bf.putShort(size);
    bf.putShort(msgType);
    bf.putShort((short)1);
    bf.put(jsonBody.getBytes());
    bf.flip();
    byte[] result = new byte[size];
    bf.get(result);
    Log.d(TAG,"msg size: "+ size + "type" + msgType + " json: " + jsonBody );
    return result;
}

Body类型¶

客户端通信消息中的Body根据Type不同，会有不同的数据结构。他们为各数据结构的Json序列化。

客户端心跳¶

客户端向服务器发送的心跳信息，同时包含一些客户端信息。

Type : 1001

Body :

class Client_Heart_Beat {
    String hardware;
    int battery_level;
    String top_apk;
    String cast_rtsp_url;  // 未 Cast 时为空字符串
    Player_Status player_info; // 可选，见下文说明
}

hardware : 设备SN号。

battery_level : 电池电量，0~100。

top_apk : 当前最上层显示的应用包名。

cast_rtsp_url : 当前 DPVR Cast 的 RTSP 地址。未开启 Cast、DMS 未连接或设备 IPv4 地址暂不可用时为空字符串；开启并收到 DMS 状态事件后，格式为 rtsp://<设备IPv4>:8554/stream1。

player_info : 可选字段，播放进度信息。仅当 top_apk 包含 com.dpvr.videoplayer （即 DPVR 播放器位于前台）且客户端已收到播放器状态时携带。

class Player_Status {
    float time;     // 当前播放位置
    float duration; // 视频总时长
    String state;   // 播放器状态
    String name;    // 视频名称
    String path;    // 视频路径
}

Note

player_info 的数值由 DPVR 播放器广播（com.dpvr.videoplayer.playerstatus）透传，客户端缓存最新值后随心跳上报；心跳周期为 2 秒，进度内容的新鲜度取决于播放器的状态广播频率。旧版服务端库会忽略该字段（保持兼容），如需解析播放进度请使用新版 LibDpvrRDC。

内容清单¶

服务端向客户端下发内容清单。客户端收到后，会为每个包含有效 content_id、file_name 和 url 的条目自动创建并启动下载任务。

Type : 4001

Body :

class Content_List {
    String sn;                 // 可选，服务端定向发送时可填写
    List<Content_Item> contents;
}

class Content_Item {
    String content_id;
    String file_name;
    String url;
    long size;
    String hash;
    String version;
}

content_id : 内容唯一标识；客户端缺少该字段时忽略该条目。

file_name : 下载后的文件名，必填；允许使用 UTF-8 文件名（包括中文），但只能填写单个文件名，不能包含 /、\、%、?、# 或 .. 等路径片段。

size、hash、version : 内容元数据；当前 RDC 客户端不会额外执行 size/hash/version 校验。

url : 下载资源地址，必填且必须使用 HTTP/HTTPS。地址原样传给设备端 DownloadService，例如 http://192.168.1.100/dpvr/demo.mp4。资源可以部署在 Nginx 或 Windows 自带的 IIS/HTTP 服务上；RDC 服务端本身不提供文件下载服务。

客户端将目标相对路径设置为 contents/<file_name>，设备端 DownloadService 将资源写入系统公共下载目录的 contents 子目录（典型路径为 /storage/emulated/0/Download/contents/<file_name>），并以 autoStart=true 自动开始下载。设备端依赖的服务组件为 com.dpvr.downloadmanager/.DownloadService。

内容状态上报¶

客户端通过内容状态消息上报下载进度。

Type : 4002

Body :

class Content_Report {
    String sn;
    List<Content_Report_Item> contents;
}

class Content_Report_Item {
    String content_id;
    String status;
    int progress;
    long downloaded;
    String local_path;
    String error;
}

status 当前由客户端映射为 pending、downloading、waiting、finished、idle 或 error；progress 为百分比，local_path 为 DownloadService 返回的本地路径。当前 downloaded 不主动计算，值保持为 0。创建任务前的校验或调用失败时，error 可能为 invalid_file_name、invalid_url 或 download_task_create_failed。客户端每 2 个心跳发送一次内容状态（心跳周期为 2 秒），没有内容条目时也发送 contents=[]。

4001 是一次性执行指令；同一 content_id 再次下发表示重新执行，客户端会通过 DownloadService Binder 移除旧任务及文件后创建新任务。客户端不因重连自动重试，也不承诺断点续传。4002 的 contents 是设备端当前记录的完整快照，不是增量；空数组会清除服务端保存的旧内容记录。

播放视频¶

服务端向客户端发送的进行视频播放消息。

Type : 1002

Body :

class Play_Video {
    String VideoType;
    String VideoPath;
    int StereoType;
    boolean StartOnPrepared = false;
}

VideoType : 视频类型，目前版本上，固定为 “*”。

VideoPath : 视频路径。

StereoType : 视频显示格式。

Note

0 : 普通2D视频。

1 ： 3D右左。

2 ： 3D上下

3： 180度2d。

4 ：180度右左3d。

5： 180度下上3d。

6： 全景2D。

7： 全景左右3D。

8： 全景上下3D。

StartOnPrepared : 是否在视频完成后自动开始播放。

视频暂停¶

服务端向客户端发送，暂停当前视频播放。

Type: 1003

Body: null

停止播放视频¶

服务端向客户端发送，停止当前视频播放。该指令仅停止播放，不影响 RDC 连接；是否同时退出播放器界面由播放器应用自身决定。

Note

客户端按 1002 最近一次消息选择的播放路由发送停止指令：使用 DPVR 播放器时发送 com.dpvr.videoplayer.VIDEOPLAYERCONTROLLER，回落到 DpnLauncher 时发送 com.deepoon.dpnlauncher.PLAY_CONTROL，并携带 controltype=playcommand、operation=stop。该指令不影响 RDC 连接；是否同时退出播放器界面由播放器应用自身决定。

Type : 1004

Body : null

恢复视频播放¶

服务端向客户端发送，在指定的统一时刻恢复当前视频播放。

Type : 1005

Body :

class Push_Resume_Video {
    String PlayTime;
}

PlayTime : 统一起播时刻，格式为 yyyy-MM-dd-HH-mm-ss 字符串（服务端本地时间，秒级精度，不含毫秒）。服务端 VideoResume(delay) 接口会将 delay``（单位：秒）加到服务端当前时间生成该值后下发，例如服务端当前时间 ``12:00:00、delay=10 时，PlayTime 为 2026-07-17-12-00-10，所有设备在本机时间到达 12:00:10 时同时恢复播放。

Note

如果需要使用定时恢复播放功能，请确保客户端系统时间与服务端一致。客户端在进行该时间判定时，如果当前时间大于设置时间，则会在收到消息时立刻进行播放。

设置按键屏蔽¶

服务端向客户端发送，设置按键屏蔽。

Type : 1008

Body :

class Push_Block_Key {
    int block_power_key;
    int block_back_key;
    int block_home_key;
    int block_touch;
    int block_volume_key;
}

block_power_key : 屏蔽电源按键，1:屏蔽，0：不屏蔽。

block_back_key : 屏蔽返回按键，1:屏蔽，0：不屏蔽。

block_home_key : 屏蔽菜单按键，1:屏蔽，0：不屏蔽。 在不带机身Home键的设备上，该项会屏蔽手柄Home键。

block_touch : 屏蔽触摸板，1:屏蔽，0：不屏蔽。

block_volume_key : 屏蔽音量按键，1:屏蔽，0：不屏蔽。

开启 DPVR Cast¶

服务端向客户端发送，调用设备端 DMS 的 DPVR Cast 接口，开启屏幕 RTSP 流。

Type : 1012

Body : 空 JSON 对象 {}。

客户端通过已有的 DeviceManager 客户端封装调用 mediaJobs/StartMiracast，不在 RDC 内重复实现 DMS 服务入口。开启结果通过 DMS 的 dpvr_cast_state 事件异步反馈，后续心跳才会更新 cast_rtsp_url。

关闭 DPVR Cast¶

服务端向客户端发送，调用设备端 DMS 的 DPVR Cast 接口，关闭屏幕 RTSP 流。

Type : 1013

Body : 空 JSON 对象 {}。

客户端通过同一封装调用 mediaJobs/StopMiracast；收到 isCasting=false 状态后，后续心跳的 cast_rtsp_url 为空字符串。

Note

RDC 客户端连接 DMS 后会调用 mediaJobs/CheckDpvrMiraCastState 初始化 Cast 状态，并监听事件 dpvr_cast_state 的 isCasting 字段。设备需要具备对应的 DMS 权限/授权；协议发送成功不等于 RTSP 流已经可用。

打开指定应用¶

服务端向客户端发送，打开指定应用。

Type : 2001

Body :

class Start_Activity {
    String packagename;
    String classname;
}

packagename : 应用包名。

classname : 需要打开的Activity类名。

Note

RDC 客户端从服务上下文启动指定组件时，会补齐 Android NEW_TASK 以及 MAIN/LAUNCHER 启动语义，以便 Android 12 和 DPVR 的普通 2D→VD 路由正常处理。DPVR 设备可能由 com.dpvr.VirtualDesktop 承载普通 2D 应用，并将目标 Activity 放在 VD display（例如 display2/display4 或设备实际分配的虚拟 display）；display0/SVR 仍保持 DpnLauncher 前台是设计行为，不应据此判定 2001 失败。目标应用和 Activity 仍需已安装、可导出并可被当前用户启动。

关闭应用¶

服务端向客户端发送，关闭指定应用。

Type : 2002

Body :

class Stop_Activity {
    String packagename;
}

packagename : 应用包名。

2002 由客户端对该包执行停止处理；它不要求 display0 的 DpnLauncher 或 VD 宿主退出，也不承诺恢复到某个特定前台界面。

常见问题¶

Q: 如果需要保证所有客户端同时开始进行视频播放，应该如何处理？

A: 我们建议采取下面两种方法进行处理：

  1. 减少服务端延迟进行不同设备间的延迟优化，请确保服务端能够将所有设备的通信延迟控制在一个相对稳定的区间，最慢收到命令的设备和最快的之间延迟不超过100ms，这样能够使得通信指令较为平稳的发送到所有设备。我们的Demo示例在由华硕AX82U提供的网络环境下，使用35台左右的设备能够保证最大的接收延迟在50ms以内。

  2. 如果服务端或者网络环境限制，无法保证所有设备低延迟，可以先发送开始播放视频指令，但是禁用StartOnPrepared。 然后通过在发送恢复播放指令时，设置恢复播放时间让所有设备同时恢复播放。

    通常来说，播放器启动需要消耗5秒左右时间，另外需要2-3秒左右时间的加载，作为参考，我们建议的恢复播放时间设置为开始播放后的10-15秒后。

Note

使用定时恢复播放功能时，请确保客户端端系统时间与服务端一致。

  1. 类似的，如果需要Seek后保持设备播放同步，也可以采取类似的措施。
